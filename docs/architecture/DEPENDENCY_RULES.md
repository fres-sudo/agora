# Dependency Rules

This document is the **authoritative reference** for what may import what in the Agora monorepo. Violations are architecture bugs, not style issues.

---

## The dependency graph

```
                    ┌────────────────────────────────┐
                    │         apps/agora             │
                    │  (entry point, no logic)       │
                    └──────┬────────────────┬────────┘
                           │                │
              ┌────────────▼────┐  ┌────────▼────────────┐
              │ features/auth   │  │ features/products   │  ...more features
              │                 │  │                     │
              │ data ←── domain │  │ data ←── domain     │
              │          ──►    │  │          ──►         │
              │       presentation  │       presentation  │
              └────────┬────────┘  └────────┬────────────┘
                       │                    │
              ┌────────▼────────────────────▼────────┐
              │              packages/*               │
              │  database  result  logger  ui_kit ... │
              └──────────────────────────────────────┘
```

## Rules by scope

### `apps/agora` (the Flutter app)

| May import | May NOT import |
|---|---|
| `features/<name>` public barrel (`<name>.dart`) | `features/<name>/lib/data/**` internals |
| `packages/<name>` | `features/<name>/lib/domain/**` directly |
| Flutter SDK, pub packages | |

The app layer should only call `FeatureX.providers` and `FeatureX.routes`. It never instantiates domain models or repositories directly.

---

### `features/<name>/lib/presentation/` (BLoCs, pages, widgets)

| May import | May NOT import |
|---|---|
| `features/<name>/lib/domain/` (models, repository interfaces) | `features/<name>/lib/data/` (DAOs, table classes, DTO internals) |
| `packages/*` | Other `features/` packages |
| Flutter SDK | |

Presentation depends on the **domain abstraction**, not the concrete data layer. This is what makes the repository pattern meaningful.

---

### `features/<name>/lib/domain/` (models, repository interfaces, mappers)

| May import | May NOT import |
|---|---|
| `packages/result` | Flutter SDK (unless unavoidable) |
| `packages/errors` | `features/<name>/lib/data/` — **exception: mappers** |
| `packages/utils` | Other `features/` packages |
| Pure Dart packages | |

**Mapper exception:** `domain/mappers/` files may import DTO types from `data/dto/` or database entity types (generated by Drift). This is intentional — the mapper defines the translation *contract*, and the input side of that contract is a data type. The mapper itself still lives in `domain/` to keep the output side (domain models) visible to `domain/` code without reaching into `data/`.

---

### `features/<name>/lib/data/` (DAOs, tables, DTOs, repository impls)

| May import | May NOT import |
|---|---|
| `packages/database` (AgoraDatabase, TableMixin) | `features/<name>/lib/presentation/` |
| `packages/result`, `packages/errors`, `packages/logger` | Other `features/` packages |
| `features/<name>/lib/domain/` (models, repository interface) | |
| `drift`, `retrofit`, `json_annotation` pub packages | |

Repository implementations in `data/repositories/` implement the interface from `domain/repositories/` and depend on DAOs from `data/sources/local/daos/`.

---

### `packages/<name>` (shared packages)

| May import | May NOT import |
|---|---|
| Other `packages/` (no cycles) | `features/` packages |
| Pub packages listed in own `pubspec.yaml` | `apps/agora` |

Package-to-package dependencies must be acyclic. Allowed dependency chains:

```
ui_kit      → theme → bloc
result      → errors
logger      → (no agora packages)
database    → result, logger, utils
auth_session → result, errors, logger
observer    → logger
```

---

## Enforcement checklist

When adding a new import, ask:

1. Is the importer in `presentation/`? → It may only import `domain/` and `packages/`.
2. Is the importer in `domain/`? → It may only import `packages/` (plus `data/dto` in mappers).
3. Is the importer in `data/`? → It may import `domain/` and `packages/`, never `presentation/`.
4. Is the importer a `package`? → It may never import a `feature`.
5. Is the importer a `feature`? → It may never import another `feature`.

If the answer to any check violates the rule, the design is wrong. Common fixes:

- **Feature A needs Feature B's model** → move the shared model to a `packages/` package.
- **Feature A needs Feature B's repository** → create a shared interface in `packages/auth_session` or a new domain package.
- **Presentation needs a DAO directly** → it should get the data via a repository; add the method there.

## File naming conventions

| Layer | Convention | Example |
|---|---|---|
| Domain model | `<entity>.dart` | `product.dart` |
| Domain repository interface | `<entity>_repository.dart` | `products_repository.dart` |
| Domain mapper | `<entity>_mapper.dart` | `product_mapper.dart` |
| Drift table | `<entity>s_table.dart` | `products_table.dart` |
| Drift DAO | `<entity>s_dao.dart` | `products_dao.dart` |
| DTO | `<entity>_dto.dart` | `product_dto.dart` |
| Repository impl | `<entity>s_repository_impl.dart` | `products_repository_impl.dart` |
| Remote data source | `<entity>s_remote_data_source.dart` | `products_remote_data_source.dart` |
| BLoC | `<entity>s_bloc.dart` / `<entity>_cubit.dart` | `products_bloc.dart` |
| Feature registration | `<feature>_feature.dart` | `products_feature.dart` |
| Barrel export | `<feature>.dart` | `products.dart` |
